## Project Overview

SPI is one of the first protocols you run into when you start talking to peripherals — displays, sensors, memory chips all speak it. It's a full-duplex, synchronous protocol, which is a fancy way of saying data goes both directions at once and everything is timed off a shared clock. I wanted to understand it properly rather than just calling a library function, so I built the **peripheral (slave)** side of an SPI interface from scratch in SystemVerilog, with no high-level abstractions doing the work for me.

The scope I set was deliberately narrow so I could focus on getting the fundamentals right: single-byte (8-bit) transfers, **SPI Mode 0** only (CPOL = 0, CPHA = 0 — clock idles low, data sampled on the rising edge), simulated in ModelSim and synthesized in Quartus Prime.

## The Signals

SPI uses four wires between a controller (master) and a peripheral (slave). Getting these straight is half the battle:

| Signal | Description |
|--------|-------------|
| `MOSI` | Master Out, Slave In — data coming from the controller |
| `MISO` | Master In, Slave Out — data going back to the controller |
| `SCLK` | Serial clock, generated by the master |
| `CS`   | Chip select, active low — pulled low to start a transaction |

My design adds two outputs on top of these: `DONE`, which goes high once a full 8-bit transfer completes, and `RECEIVED_DATA`, the register that holds the captured byte.

---

## Module Ports

Here's how the slave module is declared:

```systemverilog
module spi_slave (
    input  logic clk,       // System clock
    input  logic rst,       // Reset signal
    input  logic sclk,      // SPI clock from master
    input  logic cs,        // Active-low chip select
    input  logic mosi,      // Data from master
    output logic miso,      // Data to master
    output logic done,      // Byte transfer complete
    output logic [7:0] received_data  // Captured data
);
```

---

## FSM Design

The core of the design is a **Moore-style FSM** with three states. The slave sits in `IDLE` until the master pulls `CS` low, then moves to `RECEIVING`, where it shifts one bit in on each rising `SCLK` edge. Once 8 bits have been counted, it lands in `DONE` and asserts the `done` flag before returning to idle.

```
     +-------+       CS=0         +------------+      bit_count==7        +-------+
     | IDLE  | --------------->   | RECEIVING  |  --------------------->   | DONE  |
     +-------+                   +------------+                          +-------+
          ^                                                                  |
          |                              SCLK↑                               |
          +------------------------------------------------------------------+
```

The reason for a Moore machine here is that I wanted the outputs to depend only on the current state, which keeps the timing clean and predictable — no output glitching off the inputs mid-cycle.

## Simulation

I verified the design in ModelSim with a testbench that sends a single byte, `0x3C` (binary `00111100`), into the slave and checks what comes out the other side.

![waveform](/_projects/SPI-Implementation-SystemVerilog/waveform.png)

The waveform confirmed the behavior I was after:

- `received_data` matched the transmitted `0x3C`
- `done` asserted at exactly the right cycle, right after the 8th bit
- `CS` stayed low for the whole transaction
- `SCLK` ran slower than the system clock, as a real SPI clock would

The `.do` script I used to bring up the simulation:

```tcl
# spi_slave_wave.do
vlog ../rtl/spi_slave.sv
vlog ../tb/spi_slave_tb.sv
vsim spi_slave_tb
add wave -position insertpoint sim:/spi_slave_tb/*
run 1000ns
wave zoom full
```

## Reflection

Building SPI at the register level instead of reaching for a library made a protocol I'd only ever *used* before finally click. The parts that matter — how `CS` frames a transaction, why the clock edge you sample on is a design decision (that's the whole CPOL/CPHA story), and how a shift register plus a bit counter is really all a receiver is — are things you don't internalize until you've had to write them yourself and watch them fail in a waveform. That foundation is what makes debugging a real SPI bus, or moving on to something more complex, actually tractable.

## Future Improvements

- **Support the other three SPI modes** by parameterizing CPOL and CPHA, so the slave isn't locked to Mode 0.
- **Add multi-byte transfers** — right now it captures a single byte and stops; a real peripheral usually streams several.
- **Implement the MISO return path fully**, so the slave can send meaningful data back to the master rather than just receiving.
